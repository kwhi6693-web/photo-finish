> 默认交付最终成片及简短版本/保存状态，新成片首次交付一行可选返工提示（批量末尾统一一次），原片、对比、调整说明及其他资料仅按当次明确要求提供，内部对照与质量检查保留。
> 本交付规则统一覆盖全部现行图片美化入口、场景预设调用、单张与批量修图、构图、人像精修、操作手册、个人修图技能及项目恢复。旧资料中要求默认展开完整参数、报告或技术说明的表述，由本规则替代；历史文件只供追溯。用户当次明确要求专项交付时按其范围执行。

# 按需九宫格与导出契约

仅在用户明确要求九宫格或双平台社交包时使用。普通美化不受九张数量约束，不强制平台版、文案或逐轮批准。以下完整包格式用于该专项，保留个人风格默认和保真检查。

## 先验证九张唯一来源

只在拥有九张不同原图且每张都已通过忠实性检查时生成九宫格。为每张原图分配唯一、非空的 `source_id`；禁止用同一原图的不同裁切或重复字节填满九个位置。连拍或近似构图即使来自不同原图，也不要相邻放置。合格原图不足九张时，可以保留已完成的单图，但不得生成或宣称完成九宫格。

## 排列九个位置

1. 把主题最明确、情绪最集中的照片放在中心，作为视觉锚点。
2. 用四角建立整组的冷暖、明暗、留白与复杂度边界，避免某一角过重。
3. 交替安排远景、中景、近景和细节；在人像、环境、静物之间保留呼吸节奏。
4. 让人物视线、动作方向、道路、建筑线和其他引导线尽量朝向九宫格内部。
5. 不要把连拍、近似构图或色彩过度相似的照片放在相邻位置。
6. 实际查看两个 3×3 预览，确认顺序、节奏和独立图片一致。

## 导出两个平台版本

- 微信/朋友圈：导出九张 `1080×1080` 的 RGB、sRGB JPEG。
- Instagram：导出九张有序的 `1080×1350` 的 RGB、sRGB JPEG；这是 4:5 图集，不是把一张大图切成主页拼图。
- 两个平台目录都按顺序命名为 `01.jpg` 到 `09.jpg`，编号与 manifest 的 `order` 一一对应。
- 不拉伸图片，不误裁主体；不使用边框或生成式扩图来凑尺寸。无法安全适配时，先保留可用画幅和单图成果；用户强制平台比例且与关键内容冲突时，展示损失并请求必要取舍。

## 写 manifest

把 manifest 写成一个 JSON 对象，并包含以下字段：

- `items`：恰好九个对象，按数组顺序对应位置 1 到 9。
- 每个 item 的 `order`：整数，依次为 1 到 9。
- 每个 item 的 `source_id`：唯一、非空的原图标识。
- 每个 item 的 `master`：该位置母版的交付根目录内相对路径。
- 每个 item 的 `wechat`：对应微信 JPEG 的相对路径，文件名必须为 `01.jpg` 到 `09.jpg`。
- 每个 item 的 `instagram`：对应 Instagram JPEG 的相对路径，文件名必须为 `01.jpg` 到 `09.jpg`。
- `previews`：对象，包含 `wechat` 和 `instagram` 两个 3×3 预览的相对路径。

以下片段只示范字段形状；实际 manifest 必须把 item 补足到九个，不能直接把单项示例作为交付文件：

```json
{
  "items": [
    {
      "order": 1,
      "source_id": "source-001",
      "master": "masters/01.jpg",
      "wechat": "wechat/01.jpg",
      "instagram": "instagram/01.jpg"
    }
  ],
  "previews": {
    "wechat": "previews/wechat-grid.jpg",
    "instagram": "previews/instagram-grid.jpg"
  }
}
```

在交付前验证：`items` 数量为九、`order` 连续、`source_id` 无重复、平台文件名与编号一致、平台尺寸正确、两个预览能解码且与九张独立图片的实际顺序一致。

## 创建 layout.md

在交付根目录创建 `layout.md`，用它记录最终九宫格的实际位置和建议发布顺序。文件必须包含下面这组 validator-compatible Markdown 表头，并按从左上到右下的阅读顺序列出恰好九行：

```markdown
| order | position | source_id | master | wechat | instagram | visual_role | publish_order |
| ---: | --- | --- | --- | --- | --- | --- | ---: |
| 1 | r1c1 | source-001 | masters/01.jpg | wechat/01.jpg | instagram/01.jpg | 视觉锚点 | 1 |
```

实际文件必须补足 9 行，不能直接使用单行示例。字段规则：

- `order`：依次为 `1` 到 `9`。
- `position`：依次为 `r1c1`、`r1c2`、`r1c3`、`r2c1` 到 `r3c3`。
- `source_id`：与 manifest 对应项完全一致的唯一来源标识。
- `master`、`wechat`、`instagram`：与 manifest 对应项完全一致的交付根目录内相对路径。
- `visual_role`：非空，说明该位置承担的视觉角色；内容中不要使用竖线字符 `|`。
- `publish_order`：与实际文件顺序一致，依次为 `1` 到 `9`。

让 `layout.md` 中的九行与 manifest 的 `items` 逐项一致。交付前由 `validate-delivery.py` 检查表头、行数、位置、来源、路径、视觉角色和发布顺序；不要用 manifest 或预览图代替 `layout.md`。

## 处理部分失败

按实际交付范围检查：九宫格需要请求的平台图、预览与来源映射；只有明确要求完整双平台含文案包时才要求captions.md及下述完整包检查。承诺范围内文件缺失或失败时：

1. 保留所有已验证文件，不覆盖、不删除，也不让后续重试破坏它们。
2. 逐项列出缺失或失败文件及原因，同时注明对应平台、`order`、`source_id`、预期路径和可执行的重试动作。
3. 不得用生成填充物、重复原图、重复字节、边框或生成式扩图补齐九个位置。
4. 仅对实际要求范围宣称完成；完整双平台含文案包须全部九项、双平台、两个预览、manifest、captions.md和layout.md通过校验。

可以明确交付已验证的单图或部分文件，但必须把它们标记为部分交付，并同时附上缺失清单。

## 脚本范围

build-grid-preview.py按manifest生成预览。validate-delivery.py校验完整双平台含八组文案包；仅在用户要求该完整包时运行，要求exit code 0、Delivery is valid!及无错误。仅九宫格未要文案时，检查实际文件、尺寸、来源唯一、布局和预览，不为旧校验器强加八组文案，不声称运行过未运行的校验器。多于九张可推荐一组九张并说明其余用途，指定选片/顺序则遵从；不足九张不重复填充。
