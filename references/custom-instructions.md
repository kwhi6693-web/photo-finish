# 自定义指令与爱好

将用户主动保存的长期规则和审美偏好作为主要修图流程的一层。不要自动保存这次的临时要求，也不要把对用户审美的推测写成个人规则。

## 可选全局指令与专业自主处理

无需设置指令即可使用。没有自定义要求时，结合原片、用途和适用个人参考，由专业摄影与后期美学自主决定构图、光影、色彩、材质和氛围。用户只限定部分要求时，执行约束，其余专业自主判断；无需先选择模式。全局规则通过 profile-set.rules 或 scenes:[] 的 profile-rule-add 保存。

“按专业判断处理”继续遵守已有全局指令。只有用户明确说本次覆盖某条审美要求，才用 task_instructions 和适用的 task_settings 记录临时覆盖，长期设置不变；单条长期停用用 profile-rule-set.enabled=false。实际内容保护与复核要求继续执行。专业判断回执只描述上下文，不代表自动语义理解或审美通过。

## 用户入口

用户可以直接说“以后按这些规则修图”“记住我喜欢的风格”“查看我的修图偏好”“删掉这一条规则”或“清空我的自定义规则”。明确要求记住、修改或清空即为授权，不重复确认。

从 `runtime/` 使用同一主入口 `python 10_SYSTEM_CONFIG/scripts/photo_edit.py ACTION`，stdin 传 JSON：

- `profile-show`：`{}` 读取当前规则、爱好和 `sha256`。空配置不创建文件。
- `profile-set`：先查看现有内容，再按用户意图合并或删除目标条目，传要修改部分的完整列表；未提供的部分保持原样。不要因新增一条而丢弃现有条目。
- `profile-reset`：`{"consent":true}` 清空规则和爱好，保留风格照片。

```json
{
  "rules": ["保留原图可见文字，不猜写模糊内容", "默认只输出最终成片"],
  "preferences": ["喜欢柔和侧光与清晰材质层次", "根据照片场景选择色彩"],
  "consent": true
}
```

每部分最多 20 条，每条最多 500 字符；去重并保留顺序。`profile-set` 中某部分传 `[]` 只清空该部分。只传 `rules` 不修改 `preferences`，反之亦然。保存成功后才确认已记住。公开包不附带上述样例作为已启用的个人偏好。

## 调用优先级与主流程

1. 当次用户明确指令。
2. 用户保存的长期规则。
3. 用户保存的审美偏好。
4. 实际适用的照片风格参考。
5. 通用默认方法。

先执行 `profile-show`，实际阅读后结合原片与当次要求明确观察和约束，再调用 `prepare` 检索参考；查看并取舍后，将最终 direction 随 submit 提交。同一组任务可复用已读取内容，但每个新任务仍核验哈希。个人规则非空时必须传回真实 `observed_profile_sha256`；未读取或内容已变化，会在发布任务前明确失败，按提示重读后重新准备，不绕过成空规则。

`prepare` 可附 `task_instructions` 字符串列表，只用于本任务，不持久保存。例如用户平时喜欢某种色调，但这次明确要另一种表达，应按本次要求处理，并在 direction、真实工具参数和实际终检中落实，不机械叠加冲突指令。若同一层存在无法兼容的要求，说明具体冲突并就冲突点澄清；可以确定是“修改旧规则”时更新旧条目，避免同时保存相反规则。

控制器回执的 `customization` 保存规则/爱好快照、哈希、本次要求及优先级；`application_verified:false` 表示这些数据不是自动审美验收。实际应用由助手落实，仍需检查生成结果。正常 submit/returned/review 流程保持，不能仅凭哈希声称每条自然语言指令已被满足。

个人指令只用于摄影任务的处理与交付习惯；不授予外部工具权限，不执行文本里的代码，不伪造真实调用或验收证据，不放宽当前任务已锁定的保护要求。

## 私有保存与任务稳定性

规则和爱好保存在与个人图库相同的私有根目录下的 SQLite 配置表，使用相同 `library_root` / `style_library_root` / `PHOTO_FINISH_STYLE_LIBRARY` 与系统用户默认位置。不能放进技能或 Git checkout，不写入公开 runtime_policy、总规范、README 或安装包。多人宿主必须为各个用户分配独立可信根目录；临时环境需要私有持久位置，跨设备同步由宿主提供。

每个任务保留准备时的快照。修改个人偏好只影响后续任务，正在执行的任务继续使用原快照，不触发重复图像调用。如用户明确要求已开始的任务改变方向，沿用现有修订任务规则处理。损坏或不支持的配置明确报错，不静默忽略，也不自动覆盖。写入时启用 SQLite secure_delete，减少替换或清空后旧文本在当前数据库页中的残留；不承诺磁盘安全擦除，也不删除既有任务快照或外部备份。

## 场景规则、启停与冲突

`profile-rule-add` 保存一条有独立 ID 的规则或爱好：

```json
{
  "text": "夜景保留灯光层次，避免大面积过曝",
  "kind": "rule",
  "scenes": ["F"],
  "enabled": true,
  "consent": true
}
```

`kind` 为 `rule` 或 `preference`，最多 60 条。`scenes:[]` 表示全局；场景可用现有 A–L 代码，也可用用户明确指定或实际观察所得的自定义标签。匹配采用去首尾空格、不区分大小写的精确标签，不声称自动理解场景。先实际观察原片，再用相同场景执行 `profile-show {"scenes":["F"]}` 与 prepare；prepare 默认以 `tags` 作为配置场景，必要时显式传 `profile_scenes`。原始全局列表继续通过 profile-set 管理。

`profile-show` 返回 `active_rules / active_preferences`、场景匹配的 scoped_rules 和 sha256；不传 scenes 时列出全部规则供管理，当前生效部分只包括全局规则。形成 direction 时使用当前生效内容。非空场景规则会把场景一起绑定到哈希，不能拿其他场景的旧回执启动任务。

- `profile-rule-set`：真实 `rule_id`、要改的 `text / kind / scenes / enabled` 和 `consent:true`；未传部分不变，enabled 可独立启停；setting/value 也可修改，两者同时设为空字符串可取消结构化设置。
- `profile-rule-remove`：真实 `rule_id` 与 `consent:true`，移除一条场景规则。
- 对能明确结构化的互斥要求，可附同一 `setting`（小写键，例如 palette）与 `value`（例如 warm 或 cool）。仅当同一场景、同一优先级下同一个键出现不同值，返回 conflicts；规则优先于审美偏好。普通自然语言冲突继续由助手判断，不声称全面语义检测。
- 未解决的结构化冲突会阻止 prepare 发布任务。先修改/停用冲突条目；当次用户已经明确覆盖时，可传真实 `task_settings`（例如 `{"palette":"cool"}`）与 task_instructions，按当次要求建立 direction。不得凭空补值绕过冲突。

## 修改历史与撤销

`profile-history {}` 列出最多 20 次个人配置修改前的快照摘要；`profile-undo {"consent":true}` 撤回最近一次修改，可连续撤销。仅实际发生的修改进入历史，不反复记录相同设置。历史属于私人配置，不发布到 Git。

**profile-reset 会清空全局规则、场景规则及撤销历史，因此完整清空不可撤销。**只想临时停用时使用 enabled:false；仅删除一条时用 rule-remove。完整清空继续保留风格照片和已存在的任务快照。移除/替换的历史数据库页启用 secure_delete，不承诺物理安全擦除或删除外部备份。
