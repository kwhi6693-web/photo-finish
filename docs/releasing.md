# Publishing a release

Published stable is [v1.5.6](https://github.com/kwhi6693-web/photo-finish/releases/tag/v1.5.6). Its [preparation record](RELEASE_1_5_6_PREPARATION.md) is historical, not an instruction to rebuild or publish it again. GitHub's Release and its attachments are separate from an existing personal Skill installation. A tooling or documentation fix does not itself authorize a new Release or host installation.

The [v1.5.1 canonical finalization](RELEASE_1_5_1_FINALIZATION.md) and [preparation](RELEASE_1_5_1_PREPARATION.md) are historical records. `dist/photo-finish.zip` and its checksum intentionally retain v1.5.1. Published version directories, tags and Release attachments are frozen. The commands below apply only to an approved new release transition. The published v1.5.6 must not be rebuilt onto its existing artifacts, retagged, or treated as automatic permission to replace an installed Skill.

The public installation ZIP and a user's private backup ZIP are separate formats. Publish only the allowlisted installation artifact generated by `tools/build_release.py`.

## Safe output rules

`--output` is required. The builder never replaces an existing ZIP or checksum, including a dangling output symlink. Outputs under the repository's `dist/` must use `dist/vX.Y.Z/` matching the source's runtime version; the historical canonical `dist/` path is read-only. Choose a fresh external directory for each development build:

```bash
python tools/build_release.py --candidate --output ../photo-finish-candidate-new/photo-finish.zip
```

Replace `photo-finish-candidate-new` with a fresh directory name on subsequent runs. Candidate mode must stay outside the repository and marks the manifest `0+candidate`. It is not an installer to publish. To verify an existing staged release, run its verifier instead of rebuilding onto its files. Do not delete published artifacts to get around the output guard.

## New release procedure

1. Review the full [material map](architecture.md). Update runtime/distribution/beautification runtime versions in `runtime_policy.json`, `CHANGELOG.md` and the three README candidate notices. Keep published-stable badges truthful until publication. Run `python tools/sync_public.py` to regenerate policy mirrors and SESSION_BRIEF; the builder derives its manifest version from that brief.
2. Run the release gates from a clean checkout:

   ```bash
   python tools/doctor.py
   python tools/check_publication.py --history
   python tools/run_tests.py
   python tools/verify_release_preparation.py --candidate
   git diff --check
   ```

3. For a separately approved **new** version, replace `X.Y.Z` below with the intended source version and ensure its output pair does not already exist. Build once into the new directory, then verify it:

   ```bash
   python tools/build_release.py --output dist/vX.Y.Z/photo-finish.zip
   python tools/verify_release_preparation.py
   ```

   Commit only that new version's ZIP and checksum. Reproduce the same source in fresh external destinations and compare the bytes; existing release outputs must remain unchanged. Review the source diff and publication findings; never add private photos, settings, backups, jobs or credentials. If an unpublished candidate needs revision, use a fresh external destination for review rather than overwriting a staged pair.
4. Merge the reviewed PR after the current-head matrix passes. Select the exact verified main commit when creating the version tag and GitHub Release; do not move an existing published tag.
5. Attach the exact verified `dist/vX.Y.Z/photo-finish.zip` and its `.sha256` file for the approved new version, describe changes, installation/upgrade steps and actual validation scope, and mark a stable release as latest. Keep attachment names `photo-finish.zip` and `photo-finish.zip.sha256` unchanged. GitHub's automatic source archives are repository snapshots, not the curated skill ZIP. The formal verifier selects a tagged version directory when present and checks source, manifest and attachments without falling back after a failure.
6. Read back the release/tag target and asset names/sizes, download both attachments, and verify the ZIP against the checksum, committed bytes and manifest. Confirm that `/releases/latest` and both README `/releases/latest/download/` links resolve to the published version, and verify those downloaded bytes. Keep historical version-specific links in release notes and changelogs unchanged.

For 1.4.2 the expected installation ZIP is 463,846 bytes, has 108 entries including its manifest, and has SHA-256 `23ce92b01a3d4c01fb81203f8d943fbd80a5fe912445e65041cd46b714d0139b`. Documentation-only changes outside the package allowlist do not change this archive. Future releases must calculate their own values.

The [validation guide](validation.md) distinguishes local checks, platform CI and photographic evidence. Publishing a release does not update a user's installed skill or transfer their private collection.
