# Publishing a release

The public installation ZIP and a user's private backup ZIP are separate formats. Publish only the allowlisted installation artifact generated by `tools/build_release.py`.

1. Review the full [material map](architecture.md) and update the package version in `tools/build_release.py`, all three README version badges, `CHANGELOG.md` and `docs/validation.md`. Run `python tools/sync_public.py` when changing skill entrypoints or runtime policy mirrors.
2. Run the release gates from a clean checkout:

   ```bash
   python tools/doctor.py
   python tools/check_publication.py --history
   python tools/run_tests.py
   python tools/build_release.py --output dist/photo-finish.zip
   git diff --check
   ```

3. Commit the generated ZIP and checksum whenever packaged inputs change. Rebuilding the same source must reproduce the same bytes. Review the source diff and publication findings; never add private photos, settings, backups, jobs or credentials.
4. Merge the reviewed PR after the current-head matrix passes. Select the exact verified main commit when creating the version tag and GitHub Release; do not move an existing published tag.
5. Attach `dist/photo-finish.zip` and `dist/photo-finish.zip.sha256`, describe the changes, installation/upgrade steps and actual validation scope, and mark a stable release as latest. Keep the attachment names `photo-finish.zip` and `photo-finish.zip.sha256` unchanged: README links use `/releases/latest/download/` so the same download entrypoint follows the latest stable release. GitHub's automatic source archives are repository snapshots, not the curated skill ZIP.
6. Read back the release/tag target and asset names/sizes, download both attachments, and verify the ZIP against the checksum, committed bytes and manifest. Confirm that `/releases/latest` and both README `/releases/latest/download/` links resolve to the published version, and verify those downloaded bytes. Keep historical version-specific links in release notes and changelogs unchanged.

For 1.4.1 the expected installation ZIP is 451,187 bytes, has 106 entries including its manifest, and has SHA-256 `a5e0e10d939942ef0f189dfbb3605946f4914196fe2881157adf4120897d4921`. Documentation-only changes outside the package allowlist do not change this archive. Future releases must calculate their own values.

The [validation guide](validation.md) distinguishes local checks, platform CI and photographic evidence. Publishing a release does not update a user's installed skill or transfer their private collection.
